## Artifact Persistence

- Persist generated artifacts to disk: n
- When `y`: agents save each generate-*/review-* skill's full output (document/diagram plus

  where `<domain-folder>` is `planning-artifacts` (Haptiq Design outputs),
  `implementation-artifacts` (Haptiq Dev-BE outputs) or `qa-artifacts` (Haptiq QA outputs).
  `<artifact-type>` is the skill's output kind (e.g. `system-design`, `sequence-diagram`,

- When `n` (or unset): output stays in chat only.

### Artifact versioning — every version is frozen

- **`<N>` is an integer starting at `v1`.** Artifacts are immutable once written: a revision is
  **never** an edit to an existing file, it is a new file at the next `<N>`. Never overwrite a
  versioned artifact.
- **Before writing, look for prior versions** of the same `<slug>-<artifact-type>` in the target
  folder. If none exist, write `v1`. If they do, the highest `<N>` is the current version — write
  `<N>+1`, and state in chat which version you superseded.
- **The current version of any artifact is the one with the highest `v<N>`.** Anything reading a
  design artifact (including code-producing skills) resolves it that way, and states the exact
  filename and version it used.
- **Every persisted artifact opens with YAML frontmatter** carrying its identity and provenance:

  ```yaml
  ---
  artifact-type: data-design          # the skill's output kind
  subject: Order Service              # what it is about
  version: 2                          # integer, matches the -v<N> in the filename
  supersedes: order-service-data-design-v1.md   # or: none
  generated-by: haptiq-bmad-generate-data-design
  source-design:                      # implementation artifacts only — may be a list
    - order-service-interface-contract-v2.md
  ticket: PROJ-123                    # or: none
  ---
  ```

### Code provenance — generated source must cite its design

- Any skill that writes or modifies **source files** puts a provenance header at the top of each
  generated file, in that language's idiomatic comment/doc-comment style, naming the design document
  **with its version** and the ticket if one was given:

  ```
  Generated from design: order-service-interface-contract-v2.md (v2)
  Supporting design:     order-management-service-system-design-v1.md (v1)
  Ticket:                PROJ-123
  ```

- Cite the exact versioned filename, never a bare title — "the interface contract" is not traceable
  six months later. Where no ticket was supplied, write `Ticket: none` rather than omitting the line,
  so its absence is a recorded fact rather than an oversight.
- When a skill modifies a file that already carries a provenance header, update it to the design
  version actually worked from and keep the prior line as history rather than discarding it.

## Response style (all Haptiq agents and commands)

- **Answer in points, not paragraphs.** Bullets, short lines, or a table. Never a block of prose
  where a list would do. One idea per bullet.
- **Show the result, not the work.** Do not narrate execution — no "reading the design doc now",
  "resolving the agent block", "checking for prior versions", no step-by-step commentary on your own
  process. Do the work silently and present the finished output.
- **Lead with the bottom line.** 2–3 lines up front: what was produced or found, and the one thing
  needing attention. Then the artifact.
- **Inventory before detail.** Several files or many findings → the summary table first, detail
  beneath.
- **Keep explanation proportional.** One or two sentences of *why* for a non-obvious decision, none
  for an obvious one. Never restate what the code or table beside it already shows.
- **Always surface, never bury:** a blocked gate and what unblocks it, a file path and version once
  saved, the suggested next step, and any question you need answered. These are results, not process.
- **Brevity never costs substance.** Never drop findings, TODOs, severity rankings, behaviour-risk
  flags or coverage gaps to shorten a response. Condense the prose around them, never the content. An
  omitted Critical finding is a failure, not concision.

## Universal engineering rules

- Never commit secrets, tokens, or credentials; use the project's configured secret store.
- Errors are named and typed — no bare `Exception`/`Error` swallowing at trust boundaries.
- Non-trivial logic ships with at least one test that fails if the logic breaks.
- Follow the existing conventions of the file you're editing over introducing new patterns.

## Domain standards

## Domain standards — Business Analysis (BA)

_Contributed by the `haptiq-ba` module. `haptiq-bmad-init` appends this to project-context.md._

**PRD to Stories**
- Every story follows **"As a [role], I want [action], so that [outcome]"** — the "so that" is never optional.
- Every requirement is assessed against **INVEST** (Independent, Negotiable, Valuable, Estimable, Small, Testable) before it is drafted as a story.
- A feature that spans multiple personas/flows, or is likely to exceed **~5 story points**, is decomposed into an **Epic with 2-5 child stories** — never forced into one oversized story. If an Epic would need more than 5 children, it is split into two Epics.
- Every story carries **Gherkin acceptance criteria** (`Given / When / Then`) covering a **happy path, an error path, and at least one edge case**.
- Stories are groomed **one at a time**; each is confirmed before the next begins.
- Missing thresholds, personas, or IDs are flagged with **[NEEDS PM INPUT]** and listed as open questions — never fabricated.

**Process & Workflow Mapping**
- Exactly four diagram types are offered: **User Flow** (person-facing UI flow), **Sequence Diagram** (system/actor message exchange), **Flow Chart** (business/system logic), and **Others** (free text). Pick the type that matches the intent rather than defaulting.
- Every decision node has **all outgoing branches labelled** — no unlabelled arrow leaves a decision diamond.
- Manual steps that could be automated and every **cross-team handoff** are called out explicitly.
- One flow per file; multiple flows (e.g. admin vs end-user) are separate diagrams, not one merged oversized diagram.

**Gap Analysis & Conflict Detection**
- A gap register distinguishes three categories: **gaps** (present in one document, missing in others), **conflicts** (direct contradictions), and **inconsistent terms** (the same term used differently across documents).
- Every finding is **specific and actionable**, carries a **severity** (Critical / High / Medium / Low) justified by delivery risk, and cites its **source location**.
- No false positives — a finding that cannot be tied to a concrete document reference is dropped or marked as an assumption.

**Backlog Refinement**
- The backlog is prioritised with **MoSCoW** (Must / Should / Could / Won't) against **stated** business priorities.
- Every **Must** carries a one-line business justification.
- **Sprint-readiness is separate from priority**: a high-priority item that lacks acceptance criteria, a persona, an estimate, or has an unresolved dependency is **Not ready** and is flagged as such.
- Priority inflation (too many Musts) is challenged, not accepted.

**Maintaining Traceability Matrices**
- Every matrix links **Requirement ID → Story ID(s) → Test Case ID(s) → Coverage status** (covered / partial / missing).
- Many-to-many links are preserved — a requirement may map to several stories and a story to several requirements.
- **Orphans** (stories with no requirement, or requirements with no story/test) are flagged explicitly.
- Test-case IDs are never fabricated — uncovered requirements are marked **missing** with a proposed test, not filled with an invented ID.

**Review posture** — every finding carries a severity (Critical / High / Medium / Low) and a
specific, actionable recommendation; reviews end with an unambiguous verdict (Approve / Approve
with conditions / Reject).

## Domain standards — Design (Architecture & Design)

_Contributed by the `haptiq-design` module. `haptiq-bmad-init` appends this to project-context.md._

**System Design**
- Every system design must include a **Failure Modes table with ≥ 5 entries** covering
  infrastructure, dependency, data, traffic, and configuration failure classes.
- Every technology choice states a **rationale** and the alternatives rejected.
- **NFR targets are explicit** (availability, latency p99, throughput, RTO/RPO) and each is
  addressed in the Scalability and Failure Modes sections.
- A **Security** section is mandatory for any system handling user or personal data.
- Not "done" until Operational Concerns (monitoring, alerting, deployment, rollback, runbook
  pointers) are covered.

**Architecture Decision Records (ADR)**
- ADR documents **≥ 2 options** with pros / cons / risks.
- `Status` is always set (Proposed / Accepted / Deprecated / Superseded).
- Consequences include **≥ 1 monitoring item**.

**Integration Design**
- Every error is classified **retryable vs non-retryable**.
- Every **state-changing** operation defines an **idempotency** strategy (key + dedup window).
- A **correlation / trace ID** propagates across every integration.
- Async integrations define DLQ / poison-message handling and a schema-evolution compatibility
  mode (backward / forward / full).
- Event names use `[domain].[entity]-[past-tense-verb]` (e.g. `order.status-changed`).

**Component Design**
- Interface inputs and outputs are fully typed; all error types are **named** and classified.
- No component with 3+ unrelated responsibilities — split on SRP violation.
- Every component identifies ≥ 3 unit-test seams.

**Data Design**
- Monetary values use `NUMERIC`/`DECIMAL` — **never** `FLOAT`/`REAL`.
- Timestamps are timezone-aware (`TIMESTAMPTZ` / ISO-8601 UTC) — never naive.
- Every PII field carries: classification, legal basis, retention period.
- Soft-delete (`deleted_at`) by default for auditable entities; FK `ON DELETE` behaviour is explicit.

**Sequence / Flows**
- Every diagram includes ≥ 2 error paths and annotates timeouts on synchronous calls.
- Async (fire-and-forget) steps are annotated; `alt`/`activate` blocks are balanced.

**Service Design**
- Every blueprint has a Line-of-Visibility row and ≥ 1 evidence artefact per phase.
- Pain points are quantified; cross-team handoffs name the specific teams.

**Review posture** — every finding carries a severity (Critical / High / Medium / Low) and a
specific, actionable recommendation; reviews end with an unambiguous verdict (Approve / Approve
with conditions / Reject).

## Domain standards — Frontend Engineering (Dev-FE)

_Contributed by the `haptiq-dev-fe` module. `haptiq-bmad-init` appends this to project-context.md._

**Stack awareness** — no command assumes React + TypeScript + Jest + Storybook. Every skill resolves
the project's actual **Stack Profile** (language, state management, test runner, Storybook, styling)
before generating or reviewing, and applies only the standards that fit the resolved stack. Detection
signals and the full adaptation matrix live in `references/tech-stack-adaptation.md`.

**Generated vs hand-maintained files — verify, never guess**
- Never classify a file as generated / do-not-edit (or safe to overwrite) from its name, a script
  name (`npm run generate`, `codegen`), or how it looks — a name is a hint, not evidence.
- Confirm from the project: the generator's real output path, the file's header, and `.gitignore`
  (a tracked file usually means hand-maintained). If still ambiguous, ask. The same filename
  (e.g. a Storyblok `bloks.ts`) is generated on one project and hand-maintained on another.

**Definition of Done — verification gate before reporting "done"**
- No change is done until the project's own **typecheck + lint + tests** have each been run and
  pass — three separate gates (tsc + tests do not cover lint-only rules like `unicorn/no-null` or
  import order).
- Resolve the real commands from `package.json` `scripts` and the eslint config; run what the
  project defines. Never let silence imply a gate passed — if one can't run, name which and why.

**Greenfield project scaffolding**
- The Stack Profile is **decided, not detected** — there's no existing project to inspect. Resolve
  it per `create-project-scaffolding`'s Step 0 (explicit PRD/user requirements → an org default in
  `project-context.md` → ask), never default silently to React + TypeScript + Jest + Storybook.
- Routes/pages are derived from the PRD's actual flows — no placeholder pages, no speculative
  features the PRD doesn't describe.
- Every scaffold ships `dev`, `build`, `lint`, `test`, and (TypeScript only) `typecheck` scripts in
  `package.json` from the first commit — the same gates this domain's Definition of Done, and every
  other Dev-FE skill, depends on.
- Seed a minimal design-token file (including breakpoint values), not a full design system; add a state-management library only if the resolved Stack Profile calls for one, never speculatively.
- This is a **create-only** capability — once the project exists, subsequent work runs through
  `create-component-scaffolding` and the rest of the domain's commands rather than a
  scaffold-specific optimise/review pair.

**Components**
- Function components + hooks; in TypeScript every prop is typed via an explicit interface (no `any`,
  no implicit `children`); in JavaScript-only projects document props via `PropTypes` or JSDoc — don't
  introduce TypeScript unasked.
- All styling values come from **design tokens** — hard-coded hex/px literals are review findings.
- Every interactive element meets **WCAG 2.2 AA**: keyboard operable, visible focus, accessible name,
  4.5:1 text contrast.
- Layouts respond across the domain's standard breakpoints — mobile `<768px`, tablet `768–1023px`, desktop `≥1024px` — unless Figma specifies different breakpoints; state which was used. Breakpoints mark discrete structural shifts only — between and around them layouts stay fluid via relative units and flexbox/grid, not fixed pixel values, so any in-between viewport width also renders correctly.
- Loading, empty, and error states are explicit; new shared components ship with a story covering
  default + key variants (only where Storybook is present).

**Unit & integration tests**
- The project's configured runner (Jest or Vitest) + React Testing Library; query priority
  **role → label → text** (`data-testid` last). If no runner is configured, say so — don't generate
  tests the project can't run.
- Test **behaviour, not implementation** — no asserting internal state, no snapshot-only suites. Cover
  default render, each prop variant, interactions, and edge cases (empty / loading / error).
- Mock at module boundaries (API, router, stores) with realistic shapes — never the component under
  test; async assertions use `findBy*` / `waitFor`, never sleeps.

**PR review & code compliance** — every finding carries a **severity** (Blocker / Major / Minor / Nit),
a `file:line` anchor, and a concrete fix; type-safety regressions (`any`, `@ts-ignore`, unchecked
casts) are **Blockers**. PR descriptions state what changed, why, how it was tested, and risk/rollback.

**Code refactoring & tech debt** — backlog items carry severity, estimated effort, and the file/module
affected; a refactor PR proves behaviour is preserved (existing tests pass, coverage doesn't drop, no
dead code left).

**Debugging & RCA** — separate **symptom from root cause** and fix the cause; every fix lands with a
**regression test** that fails without it; each RCA proposes ≥ 1 prevention guard (lint rule, type
tightening, test, monitoring).

**Documentation** — component docs include a props table (name, type, default, required), ≥ 2 usage
examples that compile against the current API, and a gotchas section; refreshed whenever the public
API changes.

**Performance** — optimisations cite a **measurement** (React Profiler, Lighthouse, bundle analysis)
before and after; `memo` / `useMemo` / `useCallback` only against an identified re-render cost.

**Review posture** — every review ends with an unambiguous verdict: Approve / Approve with conditions
/ Reject.

## Domain standards — QA (Quality Engineering & Test)

_Contributed by the `haptiq-qa` module. `haptiq-bmad-init` appends this to project-context.md._

**Test Case Authoring & Design**
- Every test case states **ID, preconditions, steps, and an explicit expected result** — no
  expected result, not a test case.
- A suite covers **positive, negative, boundary, and edge** paths — plus NFR checks
  (performance, accessibility) where the story warrants them; happy-path-only is half a suite.
- Every test case **traces to a requirement or acceptance criterion** and carries a
  **risk-based priority** (P1/P2/P3 or Critical/High/Medium/Low).
- No duplicate/redundant tests; steps are unambiguous enough for someone who didn't write them.

**Writing Automation Scripts**
- Scripts use a **Page Object Model** (or equivalent) structure — no test logic tangled with
  locators.
- **No hard-coded test data** — data is externalised and reusable; **no secrets in code**.
- **Explicit waits only** — never fixed `sleep()`; synchronise on state, not on elapsed time.
- **Resilient locators** — prefer role / `data-test-id` / accessible name over brittle absolute
  XPath or volatile visible text.
- **Every expected result is asserted**; tests are independent and idempotent (order-free,
  self-cleaning); scripts are **CI/CD-ready**.

**Test Script Maintenance (Brittle Tests)**
- A flaky test is a **broken test** — fix the root cause; never retry-and-ignore.
- Every fix **classifies the cause** (test-design vs environment vs data isolation) before
  changing code, and applies explicit waits, resilient / self-healing locators, and data isolation.
- Failed tests have a **defined re-run strategy**; persistently flaky tests are **quarantined**,
  not silently disabled.

**Test Data Generation**
- Data is **schema-compliant** and covers typical, boundary (numeric/date), special-character,
  null/empty (for nullable fields), and max-length cases.
- **No real PII** — data is synthetic or masked, and complies with **data privacy / residency**
  obligations.
- Generated data is **validated against business rules**, not just types.

**Visual & UI Regression Testing**
- Triage of a visual diff must decide **intentional change vs regression** and name the likely
  responsible component before a baseline is updated.
- Visual coverage spans **layout, spacing, typography, colour, images, icons, responsive
  behaviour, element visibility, overlap/truncation**, and rendering **across browsers and
  devices/resolutions**.

**Defect Triage & Reporting**
- Every reported failure is classified **genuine defect vs test-script / environment /
  test-data issue** before it becomes a defect.
- Defects carry a **category/subcategory**, a **severity and priority** (each justified by
  business + technical impact), a **likely root cause**, an **owning component/team**, and a
  **recommended regression test**.

**Review posture** — every finding carries a severity (Critical / High / Medium / Low) and a
specific, actionable recommendation; reviews end with an unambiguous verdict (Approve / Approve
with conditions / Reject). Critical = do not proceed until resolved.
